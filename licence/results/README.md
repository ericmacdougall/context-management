# Licence rehearsal results

**Current gate statuses: `summary_current.json`.** Read this file and no other summary for a status.

- It is generated by the current code: `python3 summarize.py results --current results/summary_current.json` (run from `licence/`).
- `tests/test_evidence.py` (`test_f19_current_summary_artefact_is_what_the_code_produces`) fails if the file differs from what the code produces.
- For every life and every gate in its scope, it gives an explicit `status` (`PASS`, `FAIL` or `UNVERIFIED`) and a `reason`.
- `raw_checks` records, per life, why a figure taken from a raw file was not accepted.
- `aggregate` gives one status per gate: PASS only when every life passes, FAIL when any life fails, otherwise UNVERIFIED.

## How statuses are derived (review 9)

- **Raw rows are typed first** (`observe.parse_poll`, `observe.parse_work`).
  - Times must be finite epoch times inside the run window and in recording order, with no duplicates or overlaps.
  - Labels and HTTP statuses must agree, and arms and fields must stay in their closed domains.
  - The EXP1-T2 moments and the EXP2-T2, T3 and T5 figures are re-derived from the typed raw files at load.
  - Every stored figure a raw file can rebuild is deleted and rebuilt from that file (rule below, reviews 10 and 11). A stored value under those paths is never read, compared or kept.
- **EXP1-T3** passes only when the adapter's own `ElasticsearchSearch._is_licence_error` recognises the message the adapter would build: `HTTP <code>: ` followed by the first 400 bytes of the body.
  - The committed lives recorded only an error summary, not that message, so EXP1-T3 is UNVERIFIED for them.

## Review 10: rebuild, row schema, inventory

- **Rebuild by construction.** When a life has a raw file, the loader deletes every stored figure that the raw file can rebuild and then rebuilds all of them from typed rows. The sources are declared in `summarize.RAW_SOURCES`:
  - EXP1-T2 moments: `poll.gz`
  - EXP2-T2, T3 and T5, both directions (including the post-transition control): `rows.gz`
  - EXP2-T1: `rows.gz` plus `oracle.gz`

  Nothing stored under those paths is read.
- **Figures with no raw source.** These include matrix cells, transition times, write counts, EXP3, and T1 for lives without saved oracle legs. They are declared in `summarize.STORED`, and every verdict that reads one says "from stored figure, raw not available" in its reason. A test generated from the evidence types fails if any figure a verdict reads is undeclared.
- **Row schema.** Every workload-row field has a declared domain (`observe.ROW_FIELDS`), together with its relation to the arm and to the success state.
- **Inventory.** It comes from the campaign (`summarize.CAMPAIGN`: down_1..7 and up_1..5), not from the files found. A missing life or direction is UNVERIFIED.

## Review 11: the rule for stored figures

Stored figures under a raw source's paths are **deleted and rebuilt**, with one declared stored-only exception:

- A source's paths are deleted as soon as its key file **exists** beside the life, whether or not that file is readable. Existence is an explicit check (`summarize._present`), never an empty or failed read. The key files are `poll.gz` (EXP1-T2), `rows.gz` (EXP2-T2, T3, T5) and `oracle.gz` (EXP2-T1, which also needs `rows.gz`).
- Figures are put back only by a derivation that completes from typed rows. Any failure leaves them absent, records the reason in `raw_checks`, and makes the gate UNVERIFIED. Failures include an unreadable, truncated or non-gzip file, wrong row shape, a missing or broken companion file, a bad run window or transition time, and any exception.
- **Stored-only exceptions** (declared in `summarize.STORED`, labelled "from stored figure, raw not available" in every reason that uses them):
  - EXP2-T1 for a life with no `oracle.gz` at all (down_1..6, up_1..5: the oracle legs were not saved)
  - matrix cells, transition times, configuration, write counts and EXP3
- A life file is parsed at the boundary. If its content is not a JSON object whose `mode` matches its file name, or it cannot be read, it is an unparsed life. Every gate of it is UNVERIFIED with the reason, the aggregate names it ("does not parse"), and the other lives are still judged.

## Review 13: conjuncts, and 11 statuses changed

- **A gate passes only when every conjunct is established.** Each clause is split into its separate conditions (conjuncts). A gate is PASS only when every conjunct is ESTABLISHED from raw rows or a primary cell, FAIL when one is VIOLATED, and UNVERIFIED otherwise. `licence/CLAUSE-AUDIT.md` (generated by `audit.py`) lists each conjunct with its registered words, the code that establishes it, the raw-row test that violates it alone, and its state on every committed life (DESIGN-VERDICTS.md section 3g).
- **A clause** is FAIL only when one of its own conjuncts is VIOLATED, and PASS only when every conjunct of every gate deciding it is ESTABLISHED on every in-scope life. Clauses: 12 PASS, 2 FAIL, 62 UNVERIFIED of 76 (before: 12, 7, 56 of 75).
- **Derived figures with no raw record cannot make a PASS** (`summarize.gate_view`): EXP2-T1 for lives without `oracle.gz`, the committed `exp2.writes` counts and the EXP3 migration figures. They stay in the life files for reading. A conjunct is established only without them; a failure they record still makes the gate FAIL. down_6 EXP2-T1 is FAIL from its rows (18,820 answers, under the registered 20,000). This supersedes the review-10 and review-11 notes above: stored-only figures are no longer read for a PASS.

## Legacy tools

`summarize.py <results> <out>` (the legacy report) and `recompute.py <results> <out>` are not the status of record.
- They **refuse** `summary_current.json` as a destination: exit 2 before computing anything, with a message naming it. Only `summarize.py <results> --current <out>` writes the current report.
- On a malformed complete life (a missing or wrongly typed key) they raise an exception before opening their output file. They do not write a partial report, and they do not turn the failure into a status.
