## 0. Where this stands (one page)

### Architecture in ten lines
1. A Postgres append-only, hash-chained event log is the source of truth; Elasticsearch holds rebuildable projections, one index family per tenant (LEDGER Held).
2. A write path enforces a lease fence in the store, per-subject key destruction for erasure, legal-hold queueing and a pre-append secret scan (LEDGER write-path section).
3. Retrieval is BM25 plus dense vectors fused client-side by reciprocal rank fusion (RRF) on a Basic licence; it is an input to the context, not the memory (LEDGER Did not hold).
4. An optional asynchronous analyst tier reorders about 300 shuffled candidates; its findings arrive as ids with provenance, never on the synchronous turn path (reordering measured offline in STAGE-G; the delivery rule is v2 row 3.8.1, designed and untested, and the runtime that delivers failed review at 143fa52).
5. A typed decision log folded into a current-state table answers "what is the current position"; supersession labels are advisory and never filter (LEDGER Did-not-hold row on links; the real-session row gives the labels' hit rate).
6. Extracted facts are a lead for finding sessions that retrieval misses; they are not a proven component (STAGE-X1, STAGE-X2).
7. One policy decision point and one decision core are specified for the model port, append, projection, context assembly and inbox; both failed review for multi-tenant use (RV-POL).
8. Each turn gets a budgeted memory block injected at the model port, always well formed or empty; on Basic this is a client hook plus a pre-execution route that fails open; Agent Builder is Enterprise-optional (LEDGER Held).
9. Durable sessions run on Temporal over Postgres; a session can be rebuilt from the log (RV-ENG confirmed the rebuild; that the engine holds only ids and cursors is the design intent, not a reviewed property).
10. All model, embedding and rerank calls go through one port; subscription CLIs are development adapters only (WAL wb7ed3da806f).

### 2.2 Elasticsearch projections and the Basic path (components 4, 5, 21)
- One index family per tenant. Document-level security is not a tenant boundary because it leaks term statistics (RV-ES, reproduced). Index choice uses an immutable field, not a rolled alias or data stream (data streams accepted the same id again after a rollover).
- Recent events are read from the log tail, not from search; visibility in search is "up to the refresh interval" (replication: p50 1,002 ms with a sequential loop; 522 ms in an exploratory random-phase loop).
- Basic path (replicated on a real Basic node): BM25, kNN, rescorer, client-side fusion, quantized HNSW, `rescore_vector`, ES|QL MATCH and FORK, lexical percolator, aliases, force merge. Licence error on Basic: `rrf` and `linear` retrievers, reranker, FUSE, creating an inference endpoint, `semantic_text` indexing, `bbq_disk` (mapping accepted, 40 of 40 documents fail), document-level security.
- Degrade modes (DEGRADE.md; owner-reported, stub embedder; reviewed with limits on 2026-11-17, see the end of this bullet): a trial-to-Basic or Basic-to-trial change under load gave 0 mismatches in 387,045 responses (the original ten lives; 433,464 over all twelve) checked against an independent oracle and 0 lost among 134,290 acknowledged writes (ten lives); fallback to client fusion in 0.03 to 0.06 s. The oracle comparison was recomputed from raw rows for 1 of 12 lives (down_7: 27,599 examined, 0 mismatches). Reviewed 2026-11-17 (LAB PASS WITH LIMITS, CLIENT BLOCK): T4 on semantic writes is UNVERIFIED for all 12 lives, the migration helpers have only run against an in-memory fake, a full-row rerun was not done, and the gate fixes at 207136e are main-checked only.
- Traps found: the `linear` option on Basic silently becomes a different ranking (60 of 60 queries differ); the reviewed start-up probe never re-probes (after restart on a licensed node it stayed on the Basic path 5 of 5 times; the fix is proposed, not in reviewed code); a bulk write to a licensed vector type returns HTTP 200 with every item failed; `?q=` and plain `query_string` over a semantic-only field return HTTP 200 with 0 hits and no error (`simple_query_string`, `multi_match` and `query_string` with an explicit field return 400); the adapter reloads the system certificate store on every call (about 45 requests per second per process).
- Not tested: a licence returning on the same node (a trial cannot be restarted), trial expiry by the clock.
- ES-pilot (path item 9; eval/ES-PILOT.md at 854ed7f; reviews/eval-espilot/review-1.md and reviews/eval-espilot-delta/review-1.md; WAL w287450f28a8, wb249d9edf49): done and reviewed with limits (LAB PASS WITH LIMITS, CLIENT BLOCK, twice). 94 questions in 90 clusters, 16 cells. No MEAN-FAIL; the largest mean difference is -0.018. Three cells (BM25 at H2, BM25 at H3, cross-encoder at H3) have a mean inside the +/-0.03 band and an interval outside +/-0.05: reported as "mean within band, equivalence not demonstrated". The T4.7 reproduction tolerance was missed (0.0053 against 0.005 at H3; the cause is unverified). The needle test ran on a separate copy node of the artifacts (ES-PILOT.md lines 20 and 85), and the run was not blind (lines 8 and 81). The scorer returned KEEP on incomplete evidence at be746a0 and on 7 of 13 tampering attacks at 275f744; at 854ed7f it is bound to a committed pilot manifest and withholds on all 13 (main-verified, not re-reviewed). The manifest authenticates the files against the commit, not that the run produced them. The parity rule is decision 16 in section 7 (an ASSUMPTION, main's).
- Retrieval figures come from the exact in-process retriever. Elasticsearch BM25 shares 0.751 of the exact retriever's top 10; client RRF over the exact legs shares 0.8167 of its top 10 with Elasticsearch `rrf` (same order in 1% of questions), and client RRF over Elasticsearch's own legs equals it (1.0); a matched analyzer raises BM25 overlap to 0.9637. Replication verdict: partly (the analyzer control fell 0.082, under its 0.10 floor). `rescore_vector` oversample 3 recovers the dense loss on the owner's index but on an independent build still loses 0.039 (CI -0.078 to -0.005): it is not a general claim.

### 2.4 Fact extraction (components 16, 17, 18, 19)
- Mechanics are sound at volume: 800 of 800 calls parsed (1 repaired); quote check 0.955 raw and 0.991 after mechanical repair; 13 missing authors filled from the speaker of the cited round, 1 left unknown (STAGE-X1). In the earlier run, 2,351 of 2,373 quotes were verbatim, replicated independently; the speaker check found 8 attribution errors and 53 ambiguous cases, which go to review, not to verified.
- One session per call; batching loses facts (9.0 facts per session at 1 per call, 5.1 at 4, 4.5 at 8, 2.7 at 16; counted against an unvalidated reference). The fact cap is 30, not 12: at 12, 28% of sessions and 49% of gold sessions hit the cap. At cap 30 ordinary sessions return 11.7 facts against 8.6, so output is +33% and time +24% for every session.
- Not shown stable, on 10 long and mostly gold sessions: two runs of the identical prompt reproduce 77.6% of facts by quote match (interval by session 0.47 to 0.94; gate 85%; lowest session 51%). On those sessions a second pass adds about 31% more distinct facts; the third draw used a different prompt, so convergence is untested. Unstable facts are mostly the less important ones (73% assistant-stated against 42% of stable ones).

## 4. What is unsolved
1. **Questions retrieval cannot reach.** In the Stage G pilot 11 of 94 questions had no gold session among 300 candidates (10 of the 91 ok ones) and every arm scored 0.000 on the 10 with accepted results. Routes tried: first-stage variants (none held), deeper cross-encoder (not resolvable), two-stage (no gain), candidate depth (30% to 70% for the hard 23, never complete), analyst reordering (needs gold in the list), analyst digging (no help), facts as candidates. Facts: stopped by its rule at 2 of 11 with keyword search; 4 to 5 of 11 with dense and fused in a follow-up that only passed a screen; in X2 the lift is on questions already seen and absent on the other 12 low-overlap questions, which X1 had also used. Not established: that facts surface any session raw retrievers miss on unseen questions.
2. **Cross-session aggregation.** First-gold hit overstates what aggregation needs by about 0.3 to 0.4 at top 10; 22% of multi-session questions still miss a gold session at top 50 for every arm (X2 7.7).
3. **User preferences.** The preference content is mostly assistant-stated or mixed; the facts do not isolate the user's preference; no arm helps (X2 7.7). No design exists for it.
4. **Time anchoring.** Only 9 of 94 questions resolve a date range; a soft date feature is untested.
5. **Currency beyond typed events.** The gap in section 2.3 is specified, not built. The freshness scan has no supported result: the owner's pass was withdrawn and no real-embedder test was run (component 20). No state-accuracy benchmark was run (OPEN-QUESTIONS I1, I2).
6. **Multi-tenant hardening.** The write path (D1 to D6), the policy point (R3-1, R3-7) and the context runtime (tenant-less run key, unscoped `current_value`) each failed review on trusting callers; the composition that removes the caller-asserted identity is not built.
7. **Erasure at tenant scale.** In a 1,000,000-document tenant a 10-event subject takes 48 s, 1,000 events 90 s, and a 100,000-event subject did not finish (claim lost after 109 s). Every erasure pays a 22 to 30 s Elasticsearch retention-lease wait; another tenant waited up to 60 s for visibility during the large erasure; the test node hit its 1,000-shard limit, so a layout rule for many tenants is open (LEDGER, owner-reported).
8. **Extraction stability and cost.** 22,500 calls for the whole pool: about 333M input tokens, 51M output, 58.5 h at the observed rate, about 1,756 USD notional (X1 table); the earlier Stage X0 estimate at cap 12 was 1,630 USD and 49 h and is superseded. Event time, preferences and a stable fact set are open; one fact in four differs between runs.
9. **Judge validity.** Judged accuracy is provisional: the judge disagrees with the string heuristic on 22 to 32% of items and J1 has not run.
10. **What one host cannot prove.** All lab runs are one host or a lab node: single-node Elasticsearch with security off, a single-container Temporal server, a stand-in key store, no replicas, snapshots, failover, TLS or real model on the Agent Builder path, a shared host with timing noise, no real licence file.
