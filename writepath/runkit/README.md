# Run kit: stamped single runs (amendment 20)

Each experiment runs once, from a pinned tree, under the same validity gates as run_all (amendment 17c).

1. **Ship the clean tree.** On the workstation, `sh sync.sh` (the tree must not be dirty).
2. **Pin it.** On the host, from `WP_HOME/src`, run `sh pin_run.sh`. It prints the pinned directory `WP_HOME/runs/<head>-<time>`.
3. **Run the chain.** On the host, with `WP_HOME` set:
   `setsid sh <pinned>/runkit/chain_singles.sh <pinned> <pinned>/runkit/specs/<spec>.txt > WP_HOME/state/chain_singles.<head>.log 2>&1 < /dev/null &`
   - Each experiment goes through `launch_one.sh`:
     - It refuses to start under 20 GB free, measured in exact KiB (amendment 24; exact since H4: `df -BG` rounded up and let 19.3 GiB through).
     - It runs `exp.disk_gate start`, then `check`, the module, and `end` (gate v3, review D; design, threat model, guarantees and what is NOT covered in `runkit/GATE-DESIGN.md` section 5). The gate removes the disk hazard instead of watching for it.
     - Precondition (`host/bootstrap.py`, GATE-DESIGN 5.6): each store's data directory is a Docker tmpfs mount (`--mount type=tmpfs,destination=<data dir>,tmpfs-size=S`) in a container started with `--memory M --memory-swap M`, with S at least M + ES's low-watermark free-space threshold + 256 MiB (PG: M + 256 MiB). Every tmpfs page is charged to the container's memory limit, so nothing in the container can bring free space down to a watermark, and nothing outside it can write there. A container restart wipes the stores: setup runs again.
     - `start` is BLOCKED (exit 2) unless, for both containers by ID, Docker, the cgroup (`/proc/<pid>/cgroup`, then `memory.max`, `memory.swap.max`, `memory.peak`, `memory.events`) and the stores themselves (ES `GET _nodes/_local/stats/fs,jvm` over HTTP with the stream's admin key held in memory; PG `statfs` through `docker exec`) show that arrangement; the lifetime memory peak is within the bound; the ES API is bound to the pinned container (its 127.0.0.1 port, its JVM started with it); and, in one locked ledger step, no stop or run is open and the host has at least 20 GiB free.
     - `check` and `end` are VOID (exit 3) if any start rule fails now or anything differs from admission: container Id, StartedAt, ES node id, the cgroup's out-of-memory event count, memory limit, swap, tmpfs size, ES's thresholds; another boot; `WP_HOME` grew over 2 GiB; or a stop was recorded after admission. A VOID `check` closes the run; `end` also requires this run's admit record in the ledger.
     - Stops: an append-only, hash-chained ledger `WP_HOME/state/stop_ledger.jsonl` with a head anchor `stop_ledger.head`. A new home needs `python -m exp.disk_gate init <reason>` once (every command is BLOCKED without a ledger, and a ledger without an init record, such as a v2 ledger, is BLOCKED until `init <reason>` adopts it explicitly). Record a stop with `python -m exp.disk_gate stop <reason>`. `WP_HOME/state/STOP` is kept as a directory, so a legacy `> state/STOP` write fails loudly; a regular file found there, a file copied or moved into the directory, or a touch of it is recorded as a stop, and what was written is kept as `STOP.ingested-<seq>*`. `stops` lists unacknowledged stops (exit 2 if any); the chain runs it before each step, and `start` is BLOCKED by the same rule. `clear-stop <stop id> <reason>` acknowledges one stop and never revalidates a run it voided. `abort <reason>` closes an open run (one run at a time). A damaged ledger blocks every command until `ledger-reset <reason>`, which keeps the old file as `stop_ledger.broken-<utc>.jsonl` and starts a new ledger that names it and opens with one stop to acknowledge; `ledger-reset` refuses an intact ledger.
   - Each `.out` records `experiment_exit=<status|not run>` (the experiment's own outcome) and `gate=VALID|VOID|BLOCKED` (the gate's verdict) as separate fields; a failing cleanup stops the chain (review D F9).
   - The chain stops at the first BLOCKED or VOID run. A VOID run may be rerun, and the rerun is recorded. A FAIL is recorded and never rerun.
   - Output goes to `WP_HOME/results/one.<head>.<label>.out`, plus the experiment's own `<name>.<sha16>.json`.
4. **Scan for secrets before anything leaves the host.**
   `python3 runkit/leak_scan.py WP_HOME WP_HOME/results WP_HOME/logs WP_HOME/state <other dirs> [--keystore-container NAME] [--no-keystore REASON]`
   - Scanner v3 (review D). Its inventory comes from the secret sources, read in memory only: `WP_HOME/secrets*/` (and `WP_SECRETS_DIR` when set), `WP_HOME/oldhome/`, pgpass entries, API-key JSON (`key` and `encoded`; the key `id` is not a secret), the key store's subject and tenant keys through `docker exec <PG container> psql` (conf `pg_container`), the chain key derived from each tenant key, and, when the database `keys` exists, the keys of the legacy write path that old_repro runs. `SITES` in `leak_scan.py` names every place the stream creates a secret and how it is covered; `tests/test_leak_scan.py` fails on a site the table does not list.
   - It prints only its version and sha256, its self-test result, coverage counts, its limits, and for a hit the path, count, representation classes and source names, never a value or a fragment. A path, source name or waiver reason holding a candidate is printed as `<redacted path #n>`; a file or directory name holding one is itself a hit.
   - Exit 0 clean, 1 a hit (do not copy), 2 cannot scan or something not scanned: a missing root, a directory or file it cannot read, a non-regular file, a dangling link, a link to a directory outside the scanned roots, a damaged gzip stream, content over 512 MiB, an unreadable secret source, an unreachable key store unless `--no-keystore REASON`, an empty inventory. Every skip is listed. Only exit 0 lets results leave the host.
   - Limits, printed with every scan: a value is found when 16 consecutive characters of one listed representation appear in one normalised view; shorter pieces, encrypted content, compression other than gzip and unlisted encodings are not found. Keys the broker or a probe mints only in memory are in no file: those processes check their own output with `leak_scan.find()`, which raises on content it cannot search completely. Scans before v2 (dce5f07 and earlier) missed representations; see `results/README.md`.
5. **Copy the results to the workstation.** Copy `WP_HOME/results` to a private directory, then run
   `HOST_HOME=<host home>/ python3 runkit/stage_results.py runkit/groups.tsv <copy> <ab copy> results`.
   - It shortens the host home prefix to `~/` and writes `results/MANIFEST.tsv` with both sha256 values for every file.

`specs/step1-a.txt` to `specs/step1-f.txt` are the step-1 batches: a and b under the old gate, c (31112b4) and d (2e1948c) at the post-fix commit (amendments 23 and 23a), e (96214c2, amendment 24a) and f (the one R1 rerun at 0a433bc, amendment 24b). All were stamped under a gate with the step-1 delta review's P1 and P2 open; the hardening branch reruns the full list under the fixed gate (its H-amendment names the spec). `groups.tsv` assigns each committed result to a group and a label.
`window_check.sh` (read-only, on the host: `ssh <host> sh -s <heads...> < runkit/window_check.sh`) reads this stream's ES log over each run window again and prints, per run, the `docker logs` exit code, the line count, the high-watermark and flood-stage line counts and the own usage at `end`. It is historical: it reads wall-clock windows with `docker logs --since/--until`, which review A1 showed can conceal an in-window line, so its output is an observation about old-gate runs, never evidence for a gate verdict. Since review A the gate judges its own capture.
