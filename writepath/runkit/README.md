# Run kit: stamped single runs (amendment 20)

Each experiment runs once, from a pinned tree, under the same validity gates as run_all (amendment 17c).

1. **Ship the clean tree.** On the workstation, `sh sync.sh` (the tree must not be dirty).
2. **Pin it.** On the host, from `WP_HOME/src`, run `sh pin_run.sh`. It prints the pinned directory `WP_HOME/runs/<head>-<time>`.
3. **Run the chain.** On the host, with `WP_HOME` set:
   `setsid sh <pinned>/runkit/chain_singles.sh <pinned> <pinned>/runkit/specs/<spec>.txt > WP_HOME/state/chain_singles.<head>.log 2>&1 < /dev/null &`
   - Each experiment goes through `launch_one.sh`:
     - It refuses to start under 20 GB free, measured in exact KiB (amendment 24; exact since H4: `df -BG` rounded up and let 19.3 GiB through).
     - It runs `exp.disk_gate start`, then `check`, the module, and `end` (review A; design, threat model and guarantees in `runkit/GATE-DESIGN.md`). `start` pins both container IDs, is BLOCKED on an unsupported or non-blocking log driver or a TTY, and starts a capture companion that follows `docker logs --follow --tail 0` and `docker events` for both IDs into a hash-chained capture under `WP_HOME/state/gate-runs/<run>/`. `check` and `end` judge every captured line, not a wall-clock window: they are VOID (exit 3) on a flood-stage or high-watermark-exceeded line, a marker the gate did not write, a container event other than exec/top/archive-path (restart, stop, die, pause, update, destroy), a capture gap or edit, a companion that did not end cleanly, a different container identity at the final inspect, another boot, a host clock step, own usage not measured or over the cap, or a stop recorded after the run was admitted. A VOID `check` closes the run.
     - STOP is an append-only ledger, `WP_HOME/state/stop_ledger.jsonl`. The companion records a stop at the first flood-stage or high-watermark line it captures (there is no separate watcher). An operator records one with `python -m exp.disk_gate stop <reason>`; a legacy `WP_HOME/state/STOP` file is ingested as a stop and left in place. `python -m exp.disk_gate stops` lists unacknowledged stops (exit 2 if any); the chain runs it before each step, and `start` is BLOCKED by the same rule. Acknowledge one stop, by its id, with `python -m exp.disk_gate clear-stop <stop id> <reason>`: an acknowledgement never revalidates a run that the stop voided. `python -m exp.disk_gate abort <reason>` closes an open run (one run at a time).
   - The chain stops at the first BLOCKED or VOID run. A VOID run may be rerun, and the rerun is recorded. A FAIL is recorded and never rerun.
   - Output goes to `WP_HOME/results/one.<head>.<label>.out`, plus the experiment's own `<name>.<sha16>.json`.
4. **Scan for secrets before anything leaves the host.**
   `python3 runkit/leak_scan.py WP_HOME WP_HOME/results WP_HOME/logs WP_HOME/state <other dirs> [--keystore-container NAME] [--no-keystore REASON]`
   - Scanner v2 (review A4). Its inventory comes from the secret sources, read in memory only: `WP_HOME/secrets*/` and `WP_HOME/oldhome/` files, pgpass entries, API-key JSON (`key` and `encoded`; the key `id` is not a secret), and the key store's keys through `docker exec <PG container> psql` (conf `pg_container`). The inventory and each covered representation are in `runkit/GATE-DESIGN.md`.
   - It prints only its version and sha256, its self-test result, coverage counts, and for a hit the file, count, representation class and source name, never a value or a fragment.
   - Exit 0 clean, 1 a hit (do not copy), 2 cannot scan (an unreadable secret source, an unreachable key store unless `--no-keystore REASON`, or an empty inventory). Only exit 0 lets results leave the host.
   - Limits (review A5): it cannot check values already rotated or destroyed, keys the broker or a probe mints only in memory (those processes must check their own output with `leak_scan.find()`), or SCRAM verifiers. Scans before v2 (dce5f07 and earlier) missed representations; see `results/README.md`.
5. **Copy the results to the workstation.** Copy `WP_HOME/results` to a private directory, then run
   `HOST_HOME=<host home>/ python3 runkit/stage_results.py runkit/groups.tsv <copy> <ab copy> results`.
   - It shortens the host home prefix to `~/` and writes `results/MANIFEST.tsv` with both sha256 values for every file.

`specs/step1-a.txt` to `specs/step1-f.txt` are the step-1 batches: a and b under the old gate, c (31112b4) and d (2e1948c) at the post-fix commit (amendments 23 and 23a), e (96214c2, amendment 24a) and f (the one R1 rerun at 0a433bc, amendment 24b). All were stamped under a gate with the step-1 delta review's P1 and P2 open; the hardening branch reruns the full list under the fixed gate (its H-amendment names the spec). `groups.tsv` assigns each committed result to a group and a label.
`window_check.sh` (read-only, on the host: `ssh <host> sh -s <heads...> < runkit/window_check.sh`) reads this stream's ES log over each run window again and prints, per run, the `docker logs` exit code, the line count, the high-watermark and flood-stage line counts and the own usage at `end`. It is historical: it reads wall-clock windows with `docker logs --since/--until`, which review A1 showed can conceal an in-window line, so its output is an observation about old-gate runs, never evidence for a gate verdict. Since review A the gate judges its own capture.
