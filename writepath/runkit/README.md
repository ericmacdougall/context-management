# Run kit: stamped single runs (amendment 20)

Each experiment runs once, from a pinned tree, under the same validity gates as run_all (amendment 17c).

1. **Ship the commit.** On the workstation, `sh sync.sh`. It ships the files of the current COMMIT (never the working tree; uncommitted changes are not shipped) from git objects, with `TREE.manifest` (`runkit/tree_manifest.py`) and `GIT_HEAD`. Fixtures (every non-`.py` file under `exp/`, `wp/`, `old_repro/`, `host/`, and `requirements.lock`) must be listed with their SHA-256 in `runkit/FIXTURES.sha256`, updated in the same commit.
2. **Pin it.** On the host, from `WP_HOME/src`, run `sh pin_run.sh`. It prints the pinned directory `WP_HOME/runs/<head>-<time>` (a copy without `results/` and without bytecode caches).
3. **Run the chain.** On the host, with `WP_HOME` set:
   `setsid sh <pinned>/runkit/chain_singles.sh <pinned> <pinned>/runkit/specs/<spec>.txt > WP_HOME/state/chain_singles.<head>.log 2>&1 < /dev/null &`
   - Gate v5 (review a108fc3; design, threat model, guarantees and what is NOT covered in `runkit/GATE-DESIGN.md` section 8, storage rules in sections 5 and 6): the gate is the launcher. Before each stamped line the chain deletes the stream's indices (`exp.cleanup`) and resets the databases (`wp.setup --reset`), then runs `python -B -m exp.disk_gate run <label> <module> [args]` (also `runkit/launch_one.sh`). That one process admits the run, runs the experiment in the foreground, ends the run and exits with the verdict: 0 VALID, 3 VOID, 2 BLOCKED. The chain decides on exit statuses only.
     - Admission is BLOCKED (exit 2) unless: the tree is a pinned tree directly under `WP_HOME/runs` whose files equal its `TREE.manifest` (untracked files, `__pycache__`, a `-dirty` head refused) and whose manifest names the running gate's own SHA-256; the registered fixtures are in place; no other run holds the run lock `WP_HOME/state/run.lock` (the gate holds it for the whole run and the experiment inherits it); the stores are clean (no row outside `store_registry` in the events and keys databases, no index under `wp16096-`, nothing unregistered, an empty log store); 10 GB free, measured inside the locked admission (amendment GF1; the run stops itself under 8 GB); and every storage rule below.
     - Precondition (`host/bootstrap.py`, GATE-DESIGN 5.6 and 6.2 B4, hand-off H-8): each store's data directory is a Docker tmpfs mount with `nr_inodes=0` (no inode limit; the form is recorded in GATE-DESIGN 6.7) in a container started with `--memory M --memory-swap M`, with size S at least M + ES's low-watermark free-space threshold + 256 MiB (PG: M + 256 MiB), and nothing mounted below it. Every tmpfs page and inode is charged to the container's memory limit, so nothing in the container can bring free space down to a watermark. A container restart wipes the stores: setup runs again.
     - Storage rules (v4, unchanged): for both containers by ID: Docker shows the tmpfs mount; the container's own mount table shows one tmpfs there with `nr_inodes=0` and nothing below it; every path the store reports and every link under the mount resolve onto that tmpfs by device number (the in-container probe prints NUL-separated fields, review a108fc3 m-1); the cgroup bound holds; the PG endpoint's server reads a nonce written into the inspected container; the ES node at `es_url` is the container's node; ES's disk decider is enabled and no index is under a flood-stage block. Every gate query to PG runs under `statement_timeout` (m-6).
     - The run gets its own new directory `WP_HOME/results/runs/<run>/` and the run id (128 random bits) in `WP_RUN_DIR` and `WP_GATE_RUN`; `exp/common.write_result` writes its rows there, stamped with the run id; the experiment's stdout and stderr go to `experiment.out` there, never into the gate's lines. At the experiment's exit the run is VOID (exit 3) if a process of its group outlived it, the tree or fixtures changed, a row there names another run, a stop was recorded, or anything differs from admission (container Id, StartedAt, ES node and ephemeral id, PG system identifier, `oom` and `oom_kill`, limit, swap, tmpfs size, thresholds, ES settings and index blocks; `WP_HOME` grew over 2 GiB); the end record lists every file of the run directory with its SHA-256.
     - Stops: an append-only, hash-chained ledger `WP_HOME/state/stop_ledger.jsonl` with a head anchor `stop_ledger.head`. A new home needs `python -m exp.disk_gate init <reason>` once (every command is BLOCKED without a ledger, and a ledger without an init record, such as a v2 ledger, is BLOCKED until `init <reason>` adopts it explicitly). Record a stop with `python -m exp.disk_gate stop <reason>`. The gate never creates, reads or moves `WP_HOME/state/STOP` in normal operation: while that path exists in any form, admission is BLOCKED and an end is VOID and `stops` lists it; `clear-stop` cannot acknowledge it. Migration (every v3.0 home holds the directory v3 made): read it, then `retire-legacy-stop <reason>` moves it unread to `STOP.retired-<seq>` and records a stop to acknowledge. `stops` lists unacknowledged stops (exit 2 if any); the chain runs it before each step, and admission is BLOCKED by the same rule. `clear-stop <stop id> <reason>` acknowledges one stop and never revalidates a run it voided. `abort <run> <reason>` closes the open run `<run>` VOID only when its gate and experiment are dead (the run lock is free and its process group has no member); anything else is refused and writes nothing. `verdict <run>` prints a run's verdict from the ledger (exit 0 VALID, 3 VOID, 2 open or unknown). `start`, `check` and `end` are gone (exit 2). A damaged ledger blocks every command until `ledger-reset <reason>`, which keeps the old file as `stop_ledger.broken-<utc>.jsonl` and starts a new ledger that names it and opens with one stop to acknowledge; `ledger-reset` refuses an intact ledger.
   - Every step's output goes to its own file in a new chain directory `WP_HOME/results/chains/<utc>-<pid>/`; a rerun never overwrites an earlier attempt's record. The experiment's own outcome (`experiment_exit`) and the verdict are separate: a FAIL is a result of a VALID run.
   - The chain stops at the first non-zero status of any step (an open stop, a failed cleanup or reset, a BLOCKED or VOID run). A VOID run may be rerun, and the rerun is recorded. A FAIL is recorded and never rerun.
   - `run_all.sh` is not a stamped path since v5 (it called `start`, `check`, `end`; it now stops BLOCKED).
4. **Scan for secrets before anything leaves the host.**
   `python3 runkit/leak_scan.py WP_HOME WP_HOME/results WP_HOME/logs WP_HOME/state <other dirs> [--keystore-container NAME] [--no-keystore REASON] [--map <new file outside the roots>]`
   - Scanner v4 (review F; GATE-DESIGN 7.5). It is defence in depth: clearance rests on teardown (GATE-DESIGN 7.2 and 7.4), and the scan runs while the stores and credentials still exist. Its inventory comes from the secret sources, read in memory only: `WP_HOME/secrets*/` (and `WP_SECRETS_DIR` when set), `WP_HOME/oldhome/`, pgpass entries, API-key JSON (`key` and `encoded`; the key `id` is not a secret), the key store's subject and tenant keys through `docker exec <PG container> psql` (conf `pg_container`), the chain key derived from each tenant key, and, when the database `keys` exists, the keys of the legacy write path that old_repro runs. `SITES` in `leak_scan.py` lists every Python call that creates a secret or random value by file, enclosing function and callee with its count, and how it is covered; `check_sites()` parses the tree (import aliases and calls split across lines included) and `tests/test_leak_scan.py` fails on any difference. Shell and SQL text get a regex lint only (`LINT_SITES`).
   - It prints only its version and sha256, its self-test result, coverage counts, its limits, and entries as numbers: `file #n` in walk order, `source #k`, and for a hit `HIT file #n [name ]view <k> offset <o> inventory v<i> class <c>`. No path, name or text from a scanned tree, and no waiver reason, is printed. `--map FILE` writes the number-to-path table to a new 0600 file for local use and is refused inside a scanned root. A file or directory name holding a candidate is itself a hit, the requested roots' own paths included.
   - Exit 0 clean, 1 a hit (do not copy), 2 cannot scan or something not scanned: a missing root, a directory or file it cannot read, a non-regular file, a dangling link, a link to a directory outside the scanned roots, a damaged gzip stream, content over 512 MiB, an unreadable secret source, an unreachable key store unless `--no-keystore REASON`, an empty inventory. Every skip is listed.
   - Limits, printed with every scan and quoted here exactly: LIMITS v4 (GATE-DESIGN 7.5): found = 16 consecutive characters of one listed representation of a file-held secret (fragment class), or one complete representation of a key-store or derived key or of an encoded API key (complete class), in one view; views are the original bytes, NUL-free bytes, and unescape, percent-decode and whitespace removal in any order to depth 3, and gzip to depth 3. Not found: pieces shorter than 16 characters (of a complete-class value: anything short of the whole), encrypted content, compression other than gzip, gzip inside another encoding, deeper nesting, unlisted encodings, and values outside the inventory (memory-only keys, SCRAM internals, rotated or destroyed values). Clearance rests on teardown (runkit/clearance.py), not on this scan.
   - Keys the broker or a probe mints only in memory are in no file and in no inventory. No issuer-side check exists (review F FS2 withdrew the earlier claim); those keys die with the ES realm at teardown, and the sink (`wp/secret_sink.py`, hand-off H-2 and H-4) is prevention once wired. Scans before v2 (dce5f07 and earlier) missed representations; see `results/README.md`.
5. **Clear the set by teardown before anything leaves the host** (GATE-DESIGN 7.2 and 7.4; review F option 1). SET is `WP_HOME/results` (it holds `runs/<run>/` and `chains/`). After the chain's last run has ended, seal EVERY set the home holds while the stores are up (the first teardown destroys the stores and their credentials, and a set sealed after it has nothing to be checked against), then tear down and stage-check each:
   `python3 runkit/clearance.py seal WP_HOME SET [--keystore-container NAME | --no-keystore REASON]` for every SET, then for every SET
   `python3 runkit/clearance.py teardown WP_HOME SET --remove` and `python3 runkit/clearance.py stage-check WP_HOME SET`.
   Once a set's copy is committed, move `WP_HOME/results` aside (for example to `WP_HOME/results.cleared-<date>`) and create a new `WP_HOME/results` before the next chain: a cleared set is never sealed again.
   - seal (while the stores are up) records the set's manifest (SHA-256 per file, before and after the scan), the containers of every gate admit record since the previous receipt (every admit when there is none or the ledger was reset) and those the conf names, each inventoried credential as inventory id, class, `source #k` and SHA-256, and the scanner's result on SET. A store no gate of ledger format 3 or later admitted (a conf-named container, or one the v2 gate admitted without a tmpfs rule) must still exist and show its data directory on a private tmpfs in `docker inspect`, as the gate's B3 requires; a pre-v3 store already removed cannot be shown, so its home cannot be cleared (use a fresh home). It refuses (exit 2) a set holding a link, FIFO, socket or device, an open run, a ledger the gate's code finds damaged, a `WP_SECRETS_DIR` outside WP_HOME, and a home that is not this stream's. Exit 1 means sealed but not stageable: the scan found a value (tear down anyway), the scan could not complete (fix it and seal again BEFORE teardown, or the set can never be scanned), the seal names no store, or a store's destruction is not shown (its data on a volume, a bind mount or the container layer).
   - teardown `--remove` runs `docker rm -fv` only on sealed containers that this home's ledger admitted and whose name starts with `emlab2-wphard-` (wp/config.py `OWN_PREFIX`); a container named only by the conf is never removed (on a shared host it may be another home's store: remove it yourself if it is this home's); every sealed Id must then be absent from a successful `docker ps -a --no-trunc` (a Docker error never counts as gone), and no container may carry a conf name the seal does not hold (a store started after the seal: until H-1 bootstrap reuses the old password files). It removes every entry in `WP_HOME/secrets*`, `WP_SECRETS_DIR`, `WP_HOME/svc` and `oldhome/pgpass`, following no link and touching nothing outside WP_HOME, and refuses the receipt when a location cannot be listed or emptied (for `svc`: run h_d2_uids' root-helper cleanup first). It writes `SET/CLEARANCE.json` and `WP_HOME/state/clearance.last.json`.
   - stage-check exits 0 only when the receipt is valid, the set equals its manifest, no run was admitted after the seal on a container the receipt lacks, every receipted container is absent, the credential locations are empty, the receipt names at least one store and every store was shown to keep its data on a private tmpfs, and the recorded scan exited 0. It writes `SET/CLEARANCE.check.json` (PASS or FAIL) every time. Nothing printed or written names a path below WP_HOME or SET, or a value.
   - Limits, printed with every result and copied into every receipt: `LIMITS clearance v4` in `runkit/clearance.py` (GATE-DESIGN 7.4 and 8.2 P12, P13). The seal records the Docker daemon (ID, name, context, DOCKER_HOST, DOCKER_CONTEXT) and the names a store can carry (conf names, stream prefix): teardown and stage-check refuse another daemon or endpoint and any unsealed container under a sealed or current conf name or the prefix. `--no-keystore REASON` is recorded and is never clearance: the seal exits 1 and stage-check FAILs (key store not covered). In short: what is cleared is the stores the gate admitted or the conf names, each shown on a private tmpfs, and the listed credential locations; copies made elsewhere, data published under a key-store key, operator credentials and tampering by the same OS user are not covered.
6. **Copy the results to the workstation.** Copy `WP_HOME/results` to a private directory; run `python3 runkit/clearance.py verify-copy <copy>/<set>` on each set (receipt, PASS check bound to it, files equal to the manifest); then run
   `HOST_HOME=<host home>/ python3 runkit/stage_results.py <groups.tsv> <copy>/runs <copy of state/stop_ledger.jsonl> results` (the ledger copy with `stop_ledger.head` next to it; groups.tsv columns group, run, file, label).
   - It verifies the ledger copy (hash chain and head anchor) and stages a file only when a VALID end record lists that file of that run with that SHA-256 (GATE-DESIGN 8.2 P8); any refusal stages nothing. It shortens the host home prefix to `~/` and writes `results/MANIFEST.tsv` with both sha256 values and the end record's seq for every file. It does not yet check clearance itself or carry the CLEARANCE files (hand-off H-9).

`specs/step1-a.txt` to `specs/step1-f.txt` are the step-1 batches: a and b under the old gate, c (31112b4) and d (2e1948c) at the post-fix commit (amendments 23 and 23a), e (96214c2, amendment 24a) and f (the one R1 rerun at 0a433bc, amendment 24b). All were stamped under a gate with the step-1 delta review's P1 and P2 open; the hardening branch reruns the full list under the fixed gate (its H-amendment names the spec). `groups.tsv` assigns each committed result to a group and a label.
`window_check.sh` (read-only, on the host: `ssh <host> sh -s <heads...> < runkit/window_check.sh`) reads this stream's ES log over each run window again and prints, per run, the `docker logs` exit code, the line count, the high-watermark and flood-stage line counts and the own usage at `end`. It is historical: it reads wall-clock windows with `docker logs --since/--until`, which review A1 showed can conceal an in-window line, so its output is an observation about old-gate runs, never evidence for a gate verdict. Since review A the gate judges its own capture.
