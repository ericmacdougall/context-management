# STAGE G: one capped model-call stage on the PILOT split (design and rules, committed BEFORE any call)

Status: PILOT stage, never confirmatory. Approved by the user for this stage only, capped at 650 headless calls (user message of 2026-11-16 "Yes, run it", main WAL w517cda4...). Hard split: part A 188 calls, part B 462 calls. The frozen pre-registration (blob a72ee4563142d45b9491f1643e238d7e72b0f851) and the V2 draft are unchanged; this stage is V2's pilot A1 (analysts with shuffled candidate order and a digging prompt) plus a first answer-level look. The test split, `held_back` and `dev2` are not touched. The eval owner prepares inputs and scores; the phasef owner runs every call. Nothing in this file is a result. Section 7 is filled in (ids, sizes, depth decision) by a second commit BEFORE the first call; the rules of Sections 1 to 6 are fixed by this first commit and not changed afterwards.

## 1. Part A: analysts at the whole pool (H3), 94 pilot questions, 188 calls

Questions: all 94 pilot questions with retrieval gold (abstention excluded, as registered). Arms, one call each per question:
- A-DIG: an analyst with the registered tools over the depth-D list of RRF candidates (D chosen by the size rule below; 400 if it fits), presented in SHUFFLED order, with the digging-required prompt of Section 1.3.
- A-REORDER: the same D shuffled candidates, NO tools, the reorder prompt of Section 1.3.
Calls: 94 x 2 = 188. Budget keyed per task variant: the daemon budget key is (question, level, variant); this stage uses the variant `g` (call `analyst_tool --question <id> --level H3 --variant g`), so its 12-call budget is separate from every earlier run.

### 1.1 Candidate lists and shuffle
Candidates: the registered RRF (rank constant 60) over the exact BM25 and dense lists at H3 (fusion depth 400, output cut at D), the same object as the pilot's depth-400 baseline. Shuffle: a seeded permutation per question, `random.Random("16096:G:<question id>").shuffle`, recorded per question in `_meta.shuffle` (the list of original 1-based ranks in presented order); the original rank is never shown to the model. Task files carry the `_meta` shape (`_meta` for the runner only, never passed to a model; `question`, `question_date`, `candidates` with opaque `round_id`, `session_id`, `date`, `text`), pass the id guard, and live in `out/analyst_tasks_g/H3/<question id>.json`. Candidate text is cut by the eval owner at 400 characters per candidate (main's decision, because 1,200 characters at depth 400 would give 120,000 to 160,000 tokens per call), with the marker ' [cut]'; the digging arm can open full rounds with its tools, which is the point of the arm. The files already hold the cut text, so the runner applies no further cut.

### 1.2 Size rule (committed now; replaces the earlier 150,000-token ceiling after main's decision)
A prompt is "sane" iff its estimated size is at most 60,000 tokens: estimated tokens = sum over the D candidates of ceil(len(cut text) / 4) + 30 (the id, date and session line) + 700 (fixed prompt text). Depth D = 400 for BOTH arms if the MAXIMUM over the 94 questions is sane; otherwise D = 300 for both (and the size is stated; if 300 is also not sane it is used anyway and the size is stated). The measured sizes and the chosen D are written into Section 7 before the first call.

### 1.3 Prompts (fixed here; nothing is changed after the first call)
Version strings: `analyst-prompt-g1` (A-DIG) and `reorder-prompt-g1` (A-REORDER); the output contract of both arms is the same (main's decision): at most 20 round ids with a one-line reason each, no full ordering. System prompts are those of the frozen document (rerank system and analyst system, with "at most 12 calls" kept). N and K of the digging rule: K = 3 (fewer than three candidates that you judge to contain information that helps answer the question) and N = 3 (at least three tool calls before answering), chosen from the pilot (mean 3.6 tool calls per ok file on the low-overlap questions, 42 of 92 answers with no tool at all at H3); the maximum stays 12.
- analyst-prompt-g1 (user message): "Question (asked on {question_date}): {question}\n\nThe memory search returned the {n} candidate rounds below, in arbitrary order (round id in brackets). Many of them are probably not relevant, and the evidence needed to answer may be missing from them. You have tools: search(query, k), open_round(round_id), open_session(session_id), timeline(term). Rule: first judge how many of the candidates actually contain information that helps answer the question. If fewer than 3 do, you MUST make at least 3 tool calls (for example searches with reworded queries, or opening the sessions of promising candidates) before you answer; if 3 or more do, tool calls are optional. Use at most 12 tool calls in total. Then return at most 20 round ids, best first, each with a one-line reason. Round ids may come from the candidates or from tool results.\n\nOutput exactly: {\"results\": [{\"round_id\": \"<id>\", \"reason\": \"<one line>\"}, ...]}\n\nCandidates:\n\n{candidates}"
- reorder-prompt-g1 (user message, no tools): "Question (asked on {question_date}): {question}\n\nBelow are {n} candidate rounds from a user's chat history, in arbitrary order, each with its round id in brackets and its text cut to its first 400 characters. Most of them are probably not relevant. Return at most 20 round ids, the rounds most likely to contain the information needed to answer the question, best first, each with a one-line reason. Use only the given ids, each at most once.\n\nOutput exactly: {\"results\": [{\"round_id\": \"<id>\", \"reason\": \"<one line>\"}, ...]}\n\nCandidates:\n\n{candidates}"
- Candidate line (both): "[{round id}] {date} {session id}\n{text, cut at 400 characters with ' [cut]'}". Scoring uses the first 20 ids of either output; ids not among the candidates (or, for A-DIG, the tool results) are a rejection as before.
- Digging rule check (main's decision: enforced in the prompt, CHECKED afterwards from the tool log, not enforced by the runner; non-compliance is reported, never rejected): the model's own relevance count is not observable, so "followed" is defined mechanically: an ok A-DIG file FOLLOWS the rule iff its tool-call count (runner result and the call log rows with variant `g`) is at least N = 3. Reported: the compliance rate (share of ok A-DIG files with at least 3 tool calls), the distribution of tool calls, and two label-informed diagnostics that are descriptive only: among questions whose candidate list holds NO gold session (a weak list by the gold labels) the share that dug (at least 3 calls), and among questions whose list does hold gold the share that did not dig.

### 1.4 Results, metrics, failures
Results are written by the runner to `in/analyst_results/<ARM>/H3_g/<question id>.json` with ARM = `A-DIG` or `A-REORDER` (fields as in the earlier runs: status, ranked_round_ids, tool_calls, tokens, seconds, reasons for A-DIG). Only `ranked_round_ids` (first 20) is scored; ids must be candidates or tool-returned ids for that question (checked against the call log, rows with variant `g`), otherwise rejected and counted.
Failure handling: a result with status other than `ok`, a crash, a guard block or a timeout is a FAILURE (empty ranking: zero recall, a miss on knowledge-update) and stays in every denominator; no retries; ok-only numbers are reported beside the failures-counted ones; the rejection rate is reported per arm.
Metrics (pilot; all 94, the 23 whole-pool low-overlap questions, and the other 71, separately): session recall@10; gold session in the 4,000-token context (any gold session present; gold-session recall; gold round recall; knowledge-update gold-latest and stale-only) packed by the registered strict-prefix rule from the arm's ordered ids; tool calls and seconds per question; compliance with the digging rule. Comparators on the SAME questions: (a) RRF at the registered depth-400 ranking (the same list the analyst saw, in its unshuffled order); (b) the cross-encoder rerank v2 (head 20, 94 questions); (c) the earlier 50-candidate ANALYST and ANALYST-RERANK-ONLY results (unshuffled order), as context. Paired differences with 95% intervals by content cluster (2,000 resamples, seed 16096). Retriever: exact in-process. Primary pilot contrasts: A-DIG minus A-REORDER on session recall@10 on the 23 low-overlap questions (the digging effect), and A-REORDER minus the cross-encoder at H3 (the value of a deeper shuffled candidate list).

## 2. Part B: first answer-level look, 77 pilot questions, 462 calls

Question selection rule (written first): from the 94 pilot questions with gold, take ALL 23 whole-pool low-overlap questions (`lowoverlap_pool_h3.json`, threshold 100), ALL 15 non-abstention knowledge-update questions (none is low-overlap), and 39 more by stratified random draw by question type from the remaining 56 questions (single-session-user, single-session-assistant, single-session-preference, multi-session, temporal-reasoning): allocation proportional to the type's size in the remaining 56 by the largest-remainder rule (ties to the type name in alphabetical order); within a type, questions are ordered by sha256("16096:G:" + question id) and the first k are taken. Total 23 + 15 + 39 = 77. Abstention questions (8 in the pilot) are handled as registered: excluded from retrieval metrics and from this stage's accuracy (their precision is its own stratum and needs its own design; no calls are left for it), reported as "not run".
Context arms at H3, 4,000-token budget, each needing one reader call and one judge call (77 x 3 x 2 = 462):
- B-RRF: the registered plain retrieval context, RRF 60 packed by the registered strict-prefix rule from the depth-400 ranking (the pilot's RAG contexts at H3, 4,000 tokens).
- B-ANALYST: the context packed (4,000 tokens, same rule) from the EXISTING 50-candidate analyst H3 results (`in/analyst_results/ANALYST/H3/`), so part B does not depend on part A. A question whose analyst result was `rejected` has no context: it is a FAILURE for that arm (scored wrong without calls, counted in the denominator; the calls saved are not spent elsewhere).
- B-ORACLE: gold sessions only: the rounds that contain an evidence turn (`has_answer`) of every gold session, chronological, with dates, capped at 4,000 tokens by the same strict-prefix rule (for a knowledge-update question both the stale and the current evidence are included, the reader must pick by date). This is the headroom ceiling, not a deployable arm.
Context files are PLAIN TEXT (the exact string placed after "Context:" in the reader prompt): the packed items in chronological order, each as the rendered round "[YYYY-MM-DD HH:MM] user: ... assistant: ..." (dates for this question; distractor dates synthetic), items separated by a blank line; no ids, no arm names, no question id, no markers inside the file. The arm appears only in the path; the runner maps arms to neutral names and keeps the mapping in its ledger.
Reader and judge are both BLIND to the arm: contexts are rendered identically (same template, ids opaque, dates shown, no arm name anywhere), the arm name appears only in file paths the models never see, and the order of calls is randomised across arms by the runner (a seeded permutation of the 231 items; calls of one item are independent).
Reader: `claude-sonnet-5-5`, prompt `reader-v1.2-anon` exactly as in `phasef/prompts.py` (READER_TEMPLATE_V12; {context} = the plain-text file, {date} = the question date, {question} = the question), one call per item. Gold answers and question types come from the dataset on the Mac by pilot question id (the runner receives the 77 ids).
Judge: `claude-opus-5-5` (the judge model of the runner's earlier phase) with the LongMemEval question-type prompts exactly as in `phasef/judge.py` (`get_anscheck_prompt`, including the abstention prompt, which no question here uses; the judge system `JUDGE_SYSTEM`), ONE item per call (batch of 1), the judge sees ONLY the question, the gold answer and the reader's answer, never the arm name, the context or the question id; the verdict is yes or no.
Provisional status: the judge is NOT yet validated (V2 gate J1 has not run), so every part-B accuracy is provisional. Beside the judge's accuracy the scorer reports an exact-match or gold-string heuristic: the gold answer string (or its numbers) found in the reader's final `Answer:` line after lower-casing and punctuation stripping; not applicable to `single-session-preference` questions (the gold is a rubric), which are reported by the judge only. After scoring, 40 judged items (20 judged yes and 20 judged no, or all if fewer, drawn with seed 16096, arm hidden, with a separate key file) are written to `out/stage_g/B/audit_40.json` for a later human audit.
Failure handling (part B): a reader or judge crash, rejection, timeout or malformed output is a FAILURE (the item counts as wrong, stays in the denominator); no retries; the number of failures per arm is reported.
Metrics: judged accuracy per arm with Wilson 95% intervals by content cluster, overall and for the strata (23 low-overlap, 15 knowledge-update, the 39 others); paired differences (clustered bootstrap, 2,000 resamples, seed 16096): ORACLE minus RRF (the headroom figure), ANALYST minus RRF, ORACLE minus ANALYST; the exact-match heuristic beside each; retrieval-level numbers of the same contexts (gold session in context) beside accuracy. Retriever: exact in-process.

## 3. Calls and the cap
Part A 188 + part B at most 462 (fewer if B-ANALYST failures are scored without calls) = at most 650; the runner keeps its own counter, stops at the cap and writes the unspent remainder; no retries; no calls outside this list.

## 4. What each outcome would change in the design (stated before the run)
- A-DIG minus A-REORDER on the 23 low-overlap questions, session recall@10: at least +0.05 with a lower bound above 0: the digging prompt and tool use are kept in V2 part A with this effect as the pilot value for the A-2 threshold; upper bound below +0.03: digging adds nothing beyond reordering and V2 registers A-2 as a negative hypothesis (or drops tools); compliance (tool calls >= 3) below 0.8: the digging rule is not followed and V2 would need a tool-enforced minimum.
- A-REORDER minus the cross-encoder at H3 (all 94): at least +0.04 with a lower bound above 0: a deeper shuffled candidate list is worth a model call and the V2 candidate depth is set to the depth used here; no gain: candidate depth 400 is not adopted for the analyst arm. The shuffled arms against the earlier unshuffled 50-candidate arms tell whether anchoring on tier-0 order mattered (a drop of the same size would be the anchoring effect).
- Part B headroom (ORACLE minus RRF, judged accuracy): at least +0.10 with a lower bound above 0: the provisional G-headroom signal that a memory layer has room at H3 (still needs judge validation J1); below +0.05: answer-level parts of V2 would report cost and latency only; ANALYST minus RRF: positive and resolvable: analyst contexts go into V2 part K as extra reader contexts; not positive despite higher recall: the recall gain does not reach the answer (packing, reader or judge limits) and V2 part K must not assume it does. Heuristic and judge disagreeing on more than a fifth of the items: the judge cannot be trusted for any V2 answer claim until J1.
- None of these outcomes freezes or changes any threshold of V2 by itself; they provide the pilot values V2 says it needs (A1 and a first look at J2) and main decides what to write.

## 5. Handoff to the runner
Everything is on t2-dev under ~/emlab-16096.
- Part A task files: `out/analyst_tasks_g/H3/<question id>.json` (94): top-level keys `_meta` (question_id, level "H3", variant "g", shuffle seed and the shuffle list, depth; for the runner only, never passed to a model), `question`, `question_date`, `candidates` (list of {round_id, text (cut at 400 characters), session_id, date}, opaque ids, shuffled).
- Tool wrapper: `~/emlab-16096/bin/analyst_tool --question <question id> --level H3 --variant g` (the scope file is the registered H3 scope; the variant `g` gives a fresh daemon budget of 12 calls and 60 s per question, separate from every earlier run; call-log rows carry `variant: "g"`). The daemon was restarted on the variant-keyed code (socket ~/emlab-16096/run/analyst.sock; stop with `touch ~/emlab-16096/run/analyst.sock.stop`; start with `~/emlab-16096/bin/analyst_daemon`). The call log is ~/emlab-16096/out/analyst_calls.jsonl.
- Part A results: `in/analyst_results/A-DIG/H3_g/<question id>.json` and `in/analyst_results/A-REORDER/H3_g/<question id>.json` with fields status, ranked_round_ids (at most 20), reasons, tool_calls, tokens, seconds, prompt_version (`analyst-prompt-g1` / `reorder-prompt-g1`).
- Part B contexts (plain text): `out/stage_g/B/<ARM>/<question id>.txt` for ARM in RRF, ANALYST, ORACLE (77 questions; ANALYST has no file for a rejected analyst result, which the runner treats as a failure without calls; the question lists are in Section 7 and in `out/stage_g/B/question_ids.json`, ids, question type and stratum only).
- Part B per-item records (runner, after the arm mapping is applied): `in/stage_g/B/<ARM>/<question id>.json` with fields question_id, arm (RRF, ANALYST or ORACLE), status (ok or the failure kind), reader_answer (the full reader text), final_answer (the text after the last `Answer:`), judge (yes or no), judge_status, tokens (in, out, cache), seconds. The arm may appear in these records (the models never see it).
